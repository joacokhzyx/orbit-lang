## 1. How it compiles

Three-step sequence. The first step is NOT optional: `orbit.exe` is the seed
compiler built with Zig, and it is the only one that can propagate a source change
into the stages. If you touch any `.orb` of the compiler and do not redo step 1,
you are testing stale binaries.

```
.\orbit.exe                       build .\compiler\main.orb -o .\compiler\selfhost\stage1.exe
.\compiler\selfhost\stage1.exe    build .\compiler\main.orb -o .\compiler\selfhost\stage2.exe
.\compiler\selfhost\stage2.exe    build .\compiler\main.orb -o .\compiler\selfhost\stage3.exe
```

There is a script that runs all three and summarizes the result: `.\scratch\runall.ps1`.
(`scratch/` is local and git-ignored: if you don't have it, the three commands above
are the full flow.)

The pipeline generates C and compiles it with:
`<CC> -O0 -Wno-error=int-conversion -Wno-error=incompatible-pointer-types <cPath> -o <out> -I src/runtime [-lws2_32]`
with `CC` defaulting to `zig cc`. Each stage leaves its C next to it: `stageN.exe.c`.

### What had to be fixed to converge

The last blocker was the import resolver (`compiler/resolver.orb` +
`resolveModuleAST` in the pipeline). The `0xC0000005` crash that killed
`stage1 -> stage2` at "Resolving module imports" had two causes:

1. **Pointer truncation in the seed type inference** (`src/codegen/c_backend.zig`).
   A variable like `val decl = p.decls.get(i)` was typed `.int` by default when its
   RHS had an unknown type. Since `orbit_int` is `int` (32 bits), the `load_var` of
   `decl` emitted `(orbit_int)(uintptr_t)(decl)`, truncating the 64-bit `ASTNode*`
   pointer to 32. The `match ASTNode.ImportStmt(imp)` then read the tag of a corrupt
   pointer. Fix: the default for unknown-typed variables changed from `.int` to
   `.usize` (uintptr_t), consistent with the already existing rule "widen to 64-bit
   so pointer values are never truncated through orbit_int".
2. **Concat with int/float/bool operands** (seed and selfhost). `string_concat_mixed.orb`
   (`"total=" + total + ", ok=" + successFlag + ", ratio=" + ratio`) crashed due to
   casting/truncation of the non-string operands. Fixed in both backends
   (`boolean_literal` in the parser, `load_var` inference, `(orbit_float)` casts,
   and the concat handling in `c_backend.orb`).

`char` and `boolean` literals were also added to the selfhost (lexer/parser).

## 4. Essential context for interpreting any crash

### Why new bugs appear as we move forward

Until today's patch, destructuring of tagged unions was broken: patterns like
`ASTNode.Program(p)` compared the scrutinee tag against a freshly allocated node
pointer, so they NEVER matched and everything fell into the `_` arm.

Consequence: there are dozens of `match` arms in the compiler that had never run in
the history of this bootstrap. Now they run for the first time. Latent bugs in that
code are to be expected. Don't treat them as regressions of the patch without
evidence; most likely they are code never exercised before.

### Panic vs. silent crash

A high-value diagnostic distinction:

- **`thread NNNN panic: ...` with a trace** = Zig's UB check caught the failure in
  the C generated by our pipeline. It gives you file, line and function. Go straight
  there.
- **`0xC0000005` with no message** = the failure is in `src/runtime` (C compiled
  separately, without that instrumentation) or in a system call. Usual candidates:
  `orbit_string_concat` or `strcmp` receiving NULL.

Careful: `orbit_list_get` returns NULL when the index is out of range instead of
failing. A NULL can travel very far from the point where it originated.

### Correspondence between tags and addresses

When a panic says `misaligned address 0xNN`, that number is usually an `ASTNode`
tag used as a pointer. Convert it to decimal and look it up in this list:

```
0 Program, 1 FunctionDecl, 2 RouteDecl, 3 ModelDecl, 4 TypeDecl, 5 FieldDecl,
6 TraitDecl, 7 ImplDecl, 8 VarDecl, 9 ConstDecl, 10 ScheduleDecl, 11 ConfigDecl,
12 ImportStmt, 13 UseStmt, 14 ExpressionStmt, 15 If, 16 While, 17 For, 18 Return,
19 Match, 20 MatchCase, 21 Try, 22 Literal, 23 BinaryOp, 24 UnaryOp, 25 Call,
26 MemberAccess, 27 IndexAccess, 28 ListLiteral, 29 Assignment, 30 TypeAnnotation,
31 GenericParam, 32 Decorator, 33 Block, 34 Break, 35 Continue, 36 Param,
37 FieldInit, 38 Empty
```

That is how `0x16` = 22 = `Literal` and `0x26` = 38 = `Empty` were identified.

## 6. Bugs already fixed (don't reintroduce them)

**Bug #1 - `c_backend.orb`, `generateFunction`.** The reset of `strRegs`, `strVars`
and `declVars` and the seeding of string parameters happened AFTER
`inferRegisterTypes`. They were moved before. Symptom: string concatenation emitted
where it did not belong; `checkNode` went from 1167 to 753 lines of C.

**Bug #3 - `builder.orb`, `MemberAccess` arm of `buildExpr`.** There was a block
`if modelFieldIsUnion(...) { ... return tagReg }` that returned the tag instead of
the field. It was removed; now it does `return fieldReg`. It killed the panic
`misaligned address 0x16`.

**Bug #4 - `c_backend.orb`, `generateInstruction`.** The `lt`, `le`, `gt`, `ge`
opcodes cast to `uintptr_t`, which broke ALL the negative sentinels of the
compiler: `lookupSymbol`/`lookupFunction` (`parentId = -1` vs `scopeId >= 0`),
`findType` (`-1`), `getEnumNameFromTag` (`indexOf` -> `-1`), `generateValue`
(`if v.value < 0`). With `uintptr_t`, `-1` is huge and every ordering comparison is
inverted. Changed to `intptr_t` in those four arms. `eq` and `ne` were left intact
on purpose: they do not depend on the sign. It killed the panic `null pointer of
type 'Scope'`.

**Bug #5 - `builder.orb`, `buildMatchStatement` and `buildMatchExpr`.** The big bug.
The `ASTNode.Call(callPattern)` arm (destructuring pattern with payload) did
`val varPatReg = buildExpr(builder, callPattern.callee)` to get the value against
which to compare the tag. But `buildExpr` builds a NODE, it does not return the
integer tag, so the comparison could never be true. It was replaced by an explicit
load of the constant `tagOwner + "_TAG_" + tagName`. There is a sibling arm
`ASTNode.MemberAccess(mp)` for payload-less variants (`ASTNode.Empty =>`) that uses
the same technique and serves as a model.

This patch is what made stage2 finally reach the fixed point (306 top-level
declarations, 210 functions).

## 7. Known environment traps

**`fc` in PowerShell is not the file comparator.** It is an alias of
`Format-Custom`. To compare you must use `fc.exe`:

```
fc.exe .\compiler\selfhost\stage2.exe.c .\compiler\selfhost\stage3.exe.c
```

**Verify timestamps before drawing conclusions.** Time was already lost
diagnosing a `stage2.exe.c` that was actually from a previous run because the step
that should have regenerated it had failed. `runall.ps1` deletes `stage3.exe.c`
before running precisely for this reason.

**After each edit, re-read the edited region.** A patch was once considered
applied because the diff showed the touched areas, but only part of the change had
actually entered each area. The result was a compiler that generated a module with
zero functions and several hours lost. Don't trust the summarized diff.

**Disambiguate edits in duplicated code.** `buildMatchStatement` and
`buildMatchExpr` have byte-identical blocks. A trick that works: edit the first one
anchoring downward to a line that only exists in that function
(`buildNode(builder, c.body)` in the statement version,
`val bodyReg = buildExpr(builder, c.body)` in the expr version). Once the first is
edited, the second becomes unique and can be edited with a single-line `oldText`.

**Don't fix the `call to undeclared function 'orbit_main'` error with a
forward-declare.** That error is a SYMPTOM: it means the IR module ended up with
no functions and the generated C came out empty (30 lines instead of 45000).
Declaring `orbit_main` would hide the real problem.

## 9. Definition of done

1. Steps 1-4 run without crashing (seed -> stage1 -> stage2 -> stage3 -> stage4).
2. The compiler emits no debug/progress output on success; errors are reported
   on failure only (clean exit code 0 on success).
3. `stage3.exe.c` is byte-identical to `stage4.exe.c` (verified by SHA256).

Point 3 is the convergence gate: `stage3.exe.c` is generated by stage2 and
`stage4.exe.c` by stage3, binaries produced by different paths. If both generate
the same C, the compiler reached the fixed point.

## 10. Tools

The environment has no `grep`. Search by file name exists, but to search INSIDE
large files (the generated C is around 46000 lines) the pattern that was used is: a
PowerShell script in `scratch\` using `Get-Content` + `Select-String`, cutting line
ranges to `scratch\cut\`. There are eleven examples, `extract.ps1` to
`extract11.ps1`.

Useful detail: to locate the definition of a function in the generated C and not
get hooked by its forward declaration, require the opening brace at the end:

```powershell
Select-String -Path $c -Pattern '^static .*\bNOMBRE\s*\(.*\)\s*\{\s*$'
```
